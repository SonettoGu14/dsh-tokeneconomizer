# 测量协议与结果

状态：**协议已冻结，结果待填。** 这份文件存在的唯一目的，是回答本项目唯一还没回答
的问题：这三个机制在真实工作里到底省不省钱。机制「按规格工作」已经有 160 个单测和
11 个集成测试作证；那不等于「有用」。

先写协议再收数据，是为了让判定规则在看见数字之前就定下来——否则总能找到一种说法，
让想留的机制留下、想砍的机制砍掉。

## 需要准备的东西

1. 日常 profile 安装 `dsh-te@0.3.0`（或更高），`cost` 与 `facts` 保持默认开启。
2. `prune` **先保持关闭**，它需要单独一轮（见下），而且它是唯一会改变请求前缀的机制。
3. 选定一个真实在用的仓库作为观察对象，不要中途换。仓库身份是 key，换仓库等于清空样本。

## 数据从哪里来

全部来自日常命令，不需要额外埋点：

```sh
/te-cost repos     # 找到目标仓库的 key，以及它一共花了多少
/te-cost trend     # 逐天的等效 token、每会话中位数、cap 丢了多少条
/te-facts stats    # 每条事实的状态、注入成本、触发与浪费、盈亏平衡点
```

`trend` 的中位数已经排除了子代理会话（它们的 prompt 结构不同，混进去会把均值带偏；
总数里仍然计入，因为钱是真花的）。

## 实验一：facts 有没有用

**问题**：被注入过事实的会话，是否比「事实已存在但还没资格注入」的会话更便宜？

**样本**：目标仓库里，事实首次注入之后至少 20 个会话。

**指标**：
- 主指标：注入窗口前后各自的**每会话等效 token 中位数**（`/te-cost trend` 按天给，
  跨月份看即可；必要时从 `cost.json` 的 `history[]` 自己按天聚合）。
- 次指标：该事实的命中率在注入后是否下降。降 = 模型学会了；不降 = 事实是错的，或者
  模型无视它。两种情况都不是「省钱」。

**判定**（事先定死）：
- 中位数下降 **且** 命中率下降 → 保留，默认开启。
- 中位数下降 **但** 命中率不降 → 保留但标「待查」，因为省钱可能来自别的原因。
- 中位数不降 → 默认关闭，把阈值调高（`FIRE_GATE` / `FIRE_MIN_N`）再测一轮；连续两轮
  不降就承认这个机制在当前工作负载下不划算。

## 实验二：prune 有没有用

**问题**：藏掉闲置工具省下的 schema token，是否大于它造成的缓存失效成本？

**做法**：同一仓库，先在关闭状态记录 ≥10 个会话的基线中位数，再打开 `enabled: true`
跑 ≥10 个会话。

**指标**：中位数变化；以及缓存读占比的变化（`cost.json` 的 `buckets.cacheRead` 相对
`uncachedInput`）。藏工具会重写请求前缀，最坏情况下省下的定义 token 不够付重读的钱。

**判定**：
- 中位数下降且缓存读占比没有明显恶化 → 翻成默认 `true`，把 `idleSessions` 写进 README。
- 否则保持默认 `false`，并在 README 里写下决定它的那个数字。

## 实验三：cost 不用测

它是记账，不是机制。它是另外两个实验的仪器——这正是它先发布的原因。它唯一需要被
信任的是算术，而那部分有单测覆盖（四桶折叠、权重回落、重复结算去重）。

## 已知的混淆因素（写报告时必须声明）

- **provider 与模型变化**：不同模型价格不同，`weightsSource` 会记录回落，但换模型本身
  就会改变每会话成本。观察期内尽量不要换。
- **任务类型**：一个会话做的是「改一行」还是「重构一个模块」，比任何插件的影响都大。
  中位数只能削弱、不能消除这个影响。
- **上游缓存策略**：网关是否支持前缀缓存、TTL 多长，直接决定 `cacheRead` 占比。样本期内
  网关行为变化会让结论失真。
- **压缩器**：若同时装了 billion-context 之类的线路级压缩器，实际发出去的请求被它改写
  过，`trend` 反映的是「压缩后」的成本。要单独衡量 facts 时，最好在一轮里关掉压缩器，
  或者接受「这是压缩器在场时的组合效果」这个更弱的结论。
- **样本量**：20 个会话只能看出大效应。看不到差别时，正确的结论是「没测出来」，不是
  「没有差别」。
